两分钟讲稿

如果设计一套多渠道订阅支付，我会先定义统一 Payment API 和 PaymentProvider 接口。用户提交套餐后，服务端校验身份和价格，创建本地订阅意图。Router 按国家、币种、支付方式和渠道能力选择 PSP，再由对应 Adapter 创建托管 Checkout 并保存映射。

创建 Checkout 的同步请求返回跳转地址。Webhook 走独立入口，验签后写入 Inbox，Worker 将不同渠道的消息转成统一事件。确认实际收款后，Billing 更新 Payment、Invoice 和 Subscription，权益服务按发票与类型幂等发放 Credits。

异常里我重点看三件事。第一，同一业务请求靠业务幂等键、数据库唯一约束和渠道幂等防重复创建。第二，渠道超时代表结果未知，应固定原渠道，用原 key 重试或查询，确认旧操作终态后再决定是否换渠道。第三，Webhook 可能重复、丢失或乱序，所以我要有 Inbox、合法状态迁移和对账。

如果支付状态已经提交但权益任务没发出去，我把状态更新和 Outbox 放在同一个数据库事务，由 Relay 重试投递。消息可能重复，消费端继续凭账本唯一约束保证一次业务效果。最后对账比较 PSP、发票和已发权益，补齐长期卡住的任务。

Adapter

统一 Checkout、状态查询和事件语义。各渠道的能力、标识和幂等范围留在 Adapter 内。

Router

按国家、币种、支付方式、能力和健康度做初始选择。已经发出的尝试保留渠道归属。

State Machine

一次扣款、周期账单、长期订阅和产品权益各自迁移。续费失败可以进入宽限期。

Idempotency + Reconciliation

用持久化唯一约束阻止重复效果，定期查渠道状态和权益账本补齐遗漏。

编码面试

定义 PaymentProvider.createCheckout(command, key)、retrieve(ref) 和事件转换接口。用两个假的 Adapter 验证同一用例能够切换渠道，并测试超时映射为 UNKNOWN。

给 Webhook Inbox 加渠道事件唯一键，给权益账本加业务唯一键。测试同事件重复、不同事件指向同一发票、提交后重投，以及同一业务 key 更改参数时应拒绝。

interface PaymentProvider {
  Checkout createCheckout(Command command, String key);
  PaymentStatus retrieve(ProviderRef ref);
}
UNIQUE(provider, event_id)
UNIQUE(subscription_id, invoice_id, credit_type)
